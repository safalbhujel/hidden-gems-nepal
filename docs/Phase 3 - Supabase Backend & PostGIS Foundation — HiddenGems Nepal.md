# **1\. Phase Overview**

Phase 3 establishes the backend infrastructure required for the HiddenGems Nepal platform. The objective was not to build the application database itself, but to establish the secure and scalable foundation on which the database, authentication, geospatial discovery, user-generated content, and moderation systems will be built.

**The phase focused on:**

* Connecting Next.js App Router with Supabase.  
* Establishing secure server-side and browser-side Supabase clients.  
* Configuring environment variables and protecting privileged Supabase credentials.  
* Enabling PostgreSQL PostGIS capabilities.  
* Preparing the system for location-based discovery.  
* Creating image storage infrastructure and applying Storage Row Level Security.  
* Verifying the complete Next.js → Supabase connection.  
* Cleaning up automatically generated Supabase files that conflicted with the project's architecture.

HiddenGems Nepal's core product loop is: **Discover → View → Save/Interact → Contribute → Moderate → Publish.**

# **2\. Phase Objectives**

The following objectives were defined for Phase 3:

* **Backend Connectivity:** Connect the Next.js application to Supabase using official server/browser architecture for the Next.js App Router.  
* **Authentication Foundation:** Prepare the application for Supabase Auth and cookie-based session handling.  
* **Database Foundation:** Establish PostgreSQL as the application's database platform and enable PostGIS for geographic queries.  
* **Geospatial Foundation:** Prepare the platform for radius searches, distance calculations, and coordinate-based discovery.  
* **Storage Foundation:** Create dedicated Storage buckets for place images and user profile avatars.  
* **Security Foundation:** Implement Storage RLS policies for content protection.  
* **Architecture Consistency:** Maintain strict adherence to the lib/supabase/ architecture.

# **3\. Architecture Established**

The backend architecture follows a dual-client model to prevent server-only functionality from being mixed with browser-side functionality.

**Architecture Flow:**  
Next.js App Router&nbsp;  
→ Server Components (lib/supabase/server.ts)&nbsp;  
→ Client Components (lib/supabase/client.ts)&nbsp;  
→ Supabase SSR&nbsp;  
→ Supabase Platform (Auth, PostgreSQL, Storage)&nbsp;  
→ PostGIS

# **4\. Technology Decisions**

## **4.1 Supabase**

Supabase was selected as the backend platform to provide PostgreSQL, Authentication, Row Level Security, File storage, and PostGIS support without needing to build backend infrastructure independently.

# **5\. Dual Supabase Client Architecture**

## **5.1 Server Client (lib/supabase/server.ts)**

Responsible for Server Components, Server Actions, Route Handlers, and server-side data fetching using createServerClient from @supabase/ssr. It utilizes Next.js request cookies to maintain authenticated sessions.

## **5.2 Browser Client (lib/supabase/client.ts)**

Responsible for Client Components and browser-side authentication using createBrowserClient from @supabase/ssr. This client handles reactive authentication state and operations respecting RLS.

# **6\. Why Two Clients Are Required**

The Next.js App Router separates execution environments. The server requires access to cookies, while the browser handles authentication state and token refresh. This separation prevents accidental exposure of server-only credentials.

# **7\. Automated Wizard Cleanup**

To maintain architectural consistency, files generated by the Supabase/shadcn integration under utils/supabase/ and conflicting lib/ files were removed. The implementation was consolidated into lib/supabase/server.ts and lib/supabase/client.ts.

# **8\. Environment Variable Architecture**

The following variables were configured:

* NEXT\_PUBLIC\_SUPABASE\_URL: Identifies the project (accessible by browser-side code).  
* NEXT\_PUBLIC\_SUPABASE\_ANON\_KEY: Used by browser and public application clients. Security is enforced via RLS, not by hiding the key.  
* SUPABASE\_SERVICE\_ROLE\_KEY: Privileged server-only key. Must never be exposed to frontend code or committed to Git.
